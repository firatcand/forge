   395	## gc reconciliation rules
   396	
   397	`forge orchestrate gc` is the deterministic reconciler. Every CLI invocation may *trigger* a gc pass; an explicit `forge orchestrate gc` runs one synchronously with `--dry-run` support. The rules below are exhaustive — every state divergence has a defined resolution.
   398	
   399	### Divergence table
   400	
   401	| Local state | Tracker state | Resolution |
   402	|---|---|---|
   403	| `running` | `done` / `cancelled` / closed | Mark local terminal; release lease; archive attempt; preserve worktree for inspection (gc with `--remove-worktrees` to delete) |
   404	| `running` | no claim or claim by different `run_id` | If lease is expired beyond `steal_grace_ms`: mark `abandoned`, release lease. If lease still valid: keep local truth, log warning (tracker is the diverged party). |
   405	| `claimed` (local) | not claimed (tracker) | Re-attempt tracker claim once; if fails, mark local `unclaimed`, release lease. |
   406	| no local state | tracker claimed by *us* | Recover: write `state.json` and `lease.json` from tracker metadata. (Happens after `.forge/orchestrator/` wipe.) |
   407	| `blocked_on_question` | any | Check `.forge/orchestrator/tasks/<t>/attempts/<a>/answers/`. If answer exists, mark `awaiting_respawn`. If not and `attempt_started + question_timeout_ms` elapsed, mark `expired`. |
   408	| `ready_for_review` (local) | `done` (tracker) | Trust tracker; mark `shipped`. (Likely manual merge.) |
   409	| `shipped` | not closed | Re-check PR via tracker adapter; if PR merged, transition tracker; if not, log divergence. |
   410	| Verdict file exists but `verdict.verified.json` missing | n/a | Re-run CLI verification; write `verdict.verified.json`. |
   411	| Branch exists in repo | worktree missing | If task `shipped`: prune. If task `unclaimed` or terminal: prompt user with `--dry-run` output before pruning. |
   412	| Worktree exists | no task with matching ID in `phases.yaml` | Orphan; report. `gc --remove-orphan-worktrees` to delete. |
   413	| Question file exists | attempt is terminal | Archive the question under `attempts/<a>/archived/`. |
   414	| Answer file exists | question file is missing | Log warning; archive. (Shouldn't happen.) |
   415	| Multiple leases for same task | n/a | Only most recent `generation` is authoritative. Older leases are deleted. |
   416	| Lease present | task state is terminal | Release lease. |

   578	## Phase machine — IMPLEMENT → REVIEW → SHIP
   579	
   580	Each task flows through three phases sequentially. Each phase is its own subagent dispatch in the appropriate host.
   581	
   582	### Phase 1 — IMPLEMENT (primary host)
   583	
   584	- Dispatch skill calls `forge orchestrate next` to get a ready task.
   585	- Dispatch skill creates worktree at `.forge/worktrees/<sanitized-task-id>` via `git worktree add` (idempotent: skip if exists).
   586	- Dispatch skill calls `forge orchestrate dispatch` to register the attempt.
   587	- Subagent runs with worker prompt + task context.
   588	- On completion: subagent writes verdict.json, calls `forge orchestrate complete`, returns to parent.
   589	- CLI verifies verdict. If verified `ready_for_review`, task state advances to `ready_for_review`.
   590	
   591	### Phase 2 — REVIEW (secondary host — adversarial review)
   592	
   593	> **Cross-host direction restricted in v0.3.0.** Only `primary=Claude, review=Codex` is supported. The reverse (`primary=Codex, review=Claude`) requires spawning `claude -p` from a Codex session, which lands in Anthropic's Agent SDK quota and violates the v2 subscription-only invariant. The Codex direction is safe because OpenAI does NOT have an equivalent Agent-SDK-vs-interactive billing split — `codex exec` invoked from a Claude session bills against the user's ChatGPT Plus subscription identically to interactive Codex usage. The reverse direction unlocks in v0.3.1 alongside skill portability and proper MCP-based host bridging.
   594	
   595	- Dispatch skill detects `ready_for_review` tasks via `forge orchestrate next --phase review`.
   596	- Dispatch skill spawns a Codex subagent when primary is Claude (only supported direction in v0.3.0), with a review prompt that includes the worktree diff. Implementation: skill calls `codex exec --cd <worktree> --sandbox read-only` via Bash with the review prompt. This is subprocess dispatch in shape but subscription-billed in substance.
   597	- Review subagent reads `git diff <base>...HEAD`, runs the host's `/review` skill, writes `review_verdict.json` to the same attempt directory.
   598	- Review verdict schema:
   599	  ```ts
   600	  type ReviewVerdict = {
   601	    version: 1;
   602	    verdict: 'pass' | 'changes_requested';
   603	    findings: { severity: 'block' | 'improvement'; path: string; line?: number; message: string }[];
   604	    host: 'claude' | 'codex' | 'cursor' | 'gemini';
   605	  };
   606	  ```
   607	- `forge orchestrate complete --phase review` records the verdict.
   608	- On `pass`: task state advances to `reviewed`.
   609	- On `changes_requested`: task state regresses to `running`, a new IMPLEMENT attempt is dispatched with `priorReviewFindings` injected into the prompt. Attempt counter increments.
   610	
   611	### Phase 3 — SHIP (primary host)
   612	
   613	- Dispatch skill detects `reviewed` tasks.
   614	- **Dependency check before dispatch:** all `depends_on` tasks in `phases.yaml` must be in state `shipped` *and* their PRs merged to base. If a dependency PR is still open, SHIP is deferred until the dep merges.
   615	- Dispatch skill spawns a primary-host subagent with a ship prompt: rebase onto latest base, run final secrets scan, `gh pr create` (or tracker-equivalent), mark tracker `in_review`.

   617	- On failure (rare — usually a transient tracker/git issue): retry with backoff. After `retry_attempts` failures: task moves to `failed`, surfaces fatal notification.

   623	## Branch / PR integration topology — merge-to-main-between-phases
   624	
   625	The branch strategy: **every task branches from `main`. SHIP merges to `main`. A task with declared dependencies cannot SHIP until all dependency PRs are merged.**
   626	
   627	Rationale (chosen over stacked PRs):
   628	- Matches the dependency-graph philosophy: parallel-dispatched tasks are independent by graph construction, so they don't need to share a branch.
   629	- Eliminates rebase churn that stacked PRs require when an upstream PR is amended during review.
   630	- Each PR is reviewable in isolation against `main`.
   631	- Dependency latency is small (PR merge → next task dispatch on next `forge orchestrate next` tick).
   632	
   633	Concretely:
   634	- `forge orchestrate next` filters ready tasks to those whose `depends_on` are all `shipped` (i.e., PRs merged).
   635	- A task whose dependency is `reviewed` but PR not yet merged is **not ready** — it waits.
   636	- If a dependency PR is closed without merge: task moves to `blocked`.
   637	
   638	Trade-off accepted: tasks with declared dependencies cannot run in parallel with their dependencies even if their dependency's IMPLEMENT phase is done. This is correct — dependencies exist *because* the consumer needs the producer's output committed.
   639	
   640	For projects that want stacked PRs (rare; adds rebase loops), an opt-in `agents.branch_strategy: 'stacked'` mode is reserved in the settings schema but not implemented in v-next. Documented as a future extension if real demand emerges.

   642	## File-glob declarations + overlap detection (file-level safety)
   643	
   644	`phases.yaml` is extended to allow each task to declare its **expected write globs**:
   645	
   646	```yaml
   647	phases:
   648	  - number: 2
   649	    tasks:
   650	      - id: FORGE-31
   651	        title: Event payload schema
   652	        write_globs:
   653	          - src/schemas/events.ts
   654	          - test/schemas/events.test.ts
   655	        # ... existing fields
   656	```
   657	
   658	`write_globs` is optional. When present, `forge orchestrate next` performs an **overlap check** before dispatching parallel tasks:
   659	
   660	| Overlap class | Behavior |
   661	|---|---|
   662	| No overlap | Dispatch both freely |
   663	| Soft overlap (non-guardrail files) | Warn in dispatch output: `"FORGE-31 and FORGE-32 may both write src/utils/foo.ts — merge conflicts possible"` |
   664	| Hard overlap (any guardrail glob from preflight list) | **Block dispatch.** The task that came second in `phases.yaml` waits until the first completes. |
   665	| Either task declares a known-global file (`package.json`, lockfiles, migration directories) | Block: serialize them. |
   666	
   667	The hard-locked file list lives at `.forge/settings.yaml` → `agents.hard_lock_globs` and defaults to:
   668	```
   669	package.json
   670	package-lock.json
   671	pnpm-lock.yaml
   672	yarn.lock
   673	tsconfig.json
   674	phases.yaml
   675	src/index.ts
   676	migrations/**
   677	prisma/schema.prisma
   678	```
   679	
   680	Adopters can extend this. The principle: any file where two unrelated changes can't be merged-cleanly via git's 3-way merge belongs on this list.
   681	
   682	When `write_globs` is **absent**, the CLI assumes worst-case overlap and serializes more conservatively. This is a deliberate nudge for `/decompose` to fill in write_globs as part of task creation. v-next ships with `/decompose` updated to fill write_globs by inspection of task scope; pre-existing phases.yaml files without write_globs remain valid but get conservative scheduling.
