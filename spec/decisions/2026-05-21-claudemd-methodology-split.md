# Design: CLAUDE.md methodology split (Forge-managed `.forge/CONTEXT.md`)

**Status:** Draft — awaiting user review
**Date:** 2026-05-21
**Owner:** Firatcan (with Claude)
**Target version:** v0.5 (proposed)

---

## 1. Problem

When Forge scaffolds a product repo, it writes a single `CLAUDE.md` at the root that mixes two distinct rule sets:

- **Product rules** — how this product's code works (stack, conventions, commands, branch strategy if the team chose one).
- **Forge methodology** — how Forge builds products (8 principles, source-of-truth table, skill↔verb contract, ADR workflow, critical-paths convention).

This causes three concrete problems:

1. **Tone collision.** Product conventions read in imperative voice ("use TypeScript"); Forge methodology reads as a framework manual. Mixing them blurs which rule applies to which file.
2. **Update friction.** Forge methodology evolves with the framework. There is no way to refresh it in adopter repos without trampling user edits in the same file.
3. **Multi-agent gap.** Only Claude Code reads `CLAUDE.md`. Codex reads `AGENTS.md`. Gemini reads `GEMINI.md`. A Forge-managed repo is only fully usable by Claude users.

Roster (a downstream Forge-built product) hit all three and patched it manually. This design lifts that patch into Forge so every scaffolded repo gets the same shape natively.

## 2. Goals

- Separate Forge methodology from product rules at the file level.
- Make Forge methodology **re-syncable** across framework versions without touching product files.
- Support multiple coding agents (Claude Code, Codex CLI, Gemini CLI) in the same repo.
- Provide a discoverable breadcrumb so any agent or human encountering the repo understands it's Forge-managed and how to bootstrap.
- Keep Forge tooling state out of git; keep project config in git.

## 3. Non-goals

- Universal agent-context standardization. We pick a tool-agnostic markdown file and let each agent's root file reference it; we do not invent or push a new cross-tool standard.
- Per-agent methodology variants. The methodology prose reads identically to all agents.
- Auto-migration on `npm install` / `npm update`. Migration runs only when the user explicitly invokes `forge upgrade --migrate-claudemd`.
- Touching `spec/`, `plans/`, `CRITICAL.md`, or source code during upgrade.

## 4. Final file layout

```
<repo-root>/
├── CLAUDE.md              [tracked]    Product rules + import line (only if Claude is a configured agent)
├── AGENTS.md              [tracked]    Product rules + read-directive (only if Codex is a configured agent)
├── GEMINI.md              [tracked]    Product rules + read-directive (only if Gemini is a configured agent)
├── CRITICAL.md            [tracked]    User-curated list of critical paths (unchanged from today)
├── .gitignore             [tracked]    Contains forge-managed marker block
└── .forge/
    ├── settings.yaml      [tracked]    Project config: tracker.kind, host_cli.kind, agents.*
    ├── CONTEXT.md         [gitignored] Forge methodology + CLI/skill surface (regenerated by `forge upgrade`)
    ├── .version           [gitignored] Methodology-template version on this dev's machine
    ├── logs/              [gitignored] Existing — orchestrator run logs
    ├── worktrees/         [gitignored] Existing — task isolation
    └── .init-staging/     [gitignored] Existing — init scratch
```

### Why this shape

- **`.forge/CONTEXT.md` is gitignored.** It's framework content, not product content. Each dev's local Forge install regenerates it. Tracking it would create unwanted churn (forge release → diff in every repo) and would imply teammates can edit Forge methodology, which they cannot.
- **`.forge/settings.yaml` stays tracked.** It carries project-wide decisions (which tracker, which host CLI, which agents the team supports). These must be coherent across team and CI. Project config ≠ framework tooling.
- **Per-agent root files are tracked.** They contain the user's product rules. Forge only owns one line at the top.
- **No separate `FORGE.md` breadcrumb.** The comment block at the top of each agent root file is the breadcrumb. Avoids file count growth; the breadcrumb travels with whichever agent file the user already opens.

## 5. Per-agent root file conventions

Each root file is product-owned with one Forge-managed prefix block at the very top, delimited by markers so `forge upgrade` can refresh it without touching the rest.

### CLAUDE.md (Claude Code uses native `@import`)

```markdown
<!-- >>> forge-managed (do not edit between markers) >>> -->
> This project uses [Forge](https://github.com/firatcand/forge). The methodology
> below is imported from a local file regenerated by `forge upgrade`. If you're
> a new collaborator, install Forge with:
>
> ```
> npm install -g @firatcand/forge
> forge upgrade
> ```

@.forge/CONTEXT.md
<!-- <<< forge-managed <<< -->

# <product-name>

## Stack
...
## Conventions
...
```

### AGENTS.md (Codex — no `@import`; prose directive instead)

```markdown
<!-- >>> forge-managed (do not edit between markers) >>> -->
> This project uses [Forge](https://github.com/firatcand/forge). Before any
> work, read `.forge/CONTEXT.md` for the methodology this project follows.
> If that file is missing, install Forge with:
>
> ```
> npm install -g @firatcand/forge
> forge upgrade
> ```
<!-- <<< forge-managed <<< -->

# <product-name>

## Stack
...
```

### GEMINI.md (Gemini — same prose-directive shape as AGENTS.md)

Same template as AGENTS.md. If Gemini ships an `@import` syntax in a future release we'll switch this file to that form; the marker block lets us migrate without disturbing user prose.

### Rationale

- Forge owns the **prefix block** (between markers) — regenerated on upgrade.
- User owns **everything below** the second marker — never touched by Forge.
- The marker block doubles as the breadcrumb (visible at the top of any agent root file).

## 6. `.forge/CONTEXT.md` contents

Single tool-agnostic markdown file containing two sections:

### 6.1 Forge methodology (static template)

Bundled with the npm package as `templates/CONTEXT.template.md`. Includes:

- 8 Forge principles (Boil the Lake, Iron Law of Investigation, etc.)
- Source-of-truth table (SPEC / PRD / phases.yaml / tracker / code)
- Skill ↔ verb contract
- Ephemeral ADR workflow (when v0.5 ships)
- Branch strategy (`feat/{LINEAR-ID}-{slug}` worktree convention)
- Critical paths convention (the *meaning* of CRITICAL.md, not the list itself)

### 6.2 CLI / skill surface reference (generated)

Generated from a single source-of-truth registry inside the Forge package:

- `forge orchestrate <verb>` — claim, dispatch, complete, gc-reconcile, …
- Slash commands — `/pickup-task`, `/plan-task`, `/implement`, `/ship`, `/qa`, `/review`, …
- One-line description per item, plus pointer to deeper docs

Generated at `forge upgrade` time so it always matches the installed CLI's actual surface. Lives in the same file (one bundled artifact, one upgrade surface).

### Registry shape

Add `src/cli/registry.ts` (new file):

```typescript
export const CLI_VERBS: ReadonlyArray<{ name: string; summary: string }> = [
  { name: 'claim', summary: 'Reserve a task and create its worktree.' },
  { name: 'dispatch', summary: 'Hand the claimed task to the configured host CLI.' },
  // ...
];

export const SLASH_COMMANDS: ReadonlyArray<{ name: string; summary: string }> = [
  { name: 'pickup-task', summary: 'Claim the next ready task and pin the session into its worktree.' },
  // ...
];
```

`forge upgrade` reads this registry, renders the surface section, concatenates with the static methodology template, writes `.forge/CONTEXT.md`.

## 7. `.gitignore` marker block

Scaffold and upgrade emit (or rewrite in place) this block:

```
# >>> forge-managed (do not edit between markers) >>>
/.forge/*
!/.forge/settings.yaml
# <<< forge-managed <<<
```

Block placement:
- If `.gitignore` already contains a `# >>> forge-managed` marker → replace in place.
- If not → append at end with a leading blank line.
- User-added rules above or below the block are never touched.

## 8. `forge init` flow changes

Existing `forge init` (`src/cli/init/scaffold.ts`) gains one interactive question: **which agents this project supports**.

```
? Which coding agents will this project use? (multi-select)
  [x] Claude Code
  [ ] Codex CLI
  [ ] Gemini CLI
```

Default: whichever agent is currently invoking `forge init` (detected by env var / argv / `host_cli.kind` if already set), pre-checked.

Outcomes per selected agent:
- Adds the kind to `.forge/settings.yaml` `agents.enabled[]`.
- Writes (or, if file exists, prepends the marker block to) the corresponding root file:
  - Claude Code → `CLAUDE.md` (with `@.forge/CONTEXT.md` import)
  - Codex CLI → `AGENTS.md` (with prose directive)
  - Gemini CLI → `GEMINI.md` (with prose directive)
- All selected agents share one `.forge/CONTEXT.md` — written once regardless of selection count.

Then `init` also:
- Writes `.forge/.version` with the current bundled methodology-template version.
- Emits the `.gitignore` marker block.
- Writes the trimmed product `CLAUDE.md` template (only the agent's root file the user kept; product content from `templates/CLAUDE.project.template.md` minus everything that moved to `CONTEXT.md`).

## 9. `forge upgrade` verb

New CLI surface: `forge upgrade [flags]`. Lives at `src/cli/upgrade/upgrade.ts`.

### Default behavior (no flags)

1. Read `.forge/.version`. Compare to bundled template version.
2. Read `.forge/CONTEXT.md` if present. Compute SHA-256 over its contents.
3. **Strict edit detection**: if the on-disk SHA does not match the SHA of the bundled template at the on-disk version → refuse with a diff and exit non-zero. User must either revert local edits or pass `--force`.
4. Read `.forge/settings.yaml` `agents.enabled[]`. For each enabled agent, read the agent root file and check that the marker block matches the bundled prefix at the on-disk version.
   - If any agent root file's prefix block has been edited → refuse with diff. `--force` overrides.
5. If all checks pass:
   - Rewrite `.forge/CONTEXT.md` from `templates/CONTEXT.template.md` + generated CLI surface section.
   - Rewrite the prefix block in each enabled agent's root file (between markers).
   - Rewrite the marker block in `.gitignore`.
   - Update `.forge/.version`.
   - Print summary: which files changed, which version moved to which.

### Flags

| Flag | Effect |
|------|--------|
| `--force` | Override edit-detection refusal. Saves the user-edited file as `<path>.bak` before overwriting. |
| `--dry-run` | Print what would change, do not write. |
| `--migrate-claudemd` | One-shot legacy-layout migration (see §10). Refused if `.forge/CONTEXT.md` already exists. |
| `--add-agent <kind>` | Add a new agent (`claude_code`/`codex`/`gemini`) to `agents.enabled[]` and write its root file. Idempotent. |
| `--remove-agent <kind>` | Remove an agent from `agents.enabled[]`. Saves the root file as `<path>.pre-removal.bak` before deletion. Refuses without confirmation if the file's body (below the marker block) is non-empty. |

### Refusals & exit codes

- `0` — success or no-op.
- `1` — user-edit detected without `--force`.
- `2` — uncommitted changes or active worktree leases (configurable; `--force` overrides).
- `3` — `.forge/settings.yaml` missing or malformed (run `forge init` first).
- `4` — methodology version on disk is newer than bundled (CLI too old; tells user to update npm package).

### CLI version drift warning

On every `forge <any-verb>` invocation (not just upgrade), the CLI:
1. Reads `.forge/.version` if present.
2. Compares to bundled methodology version.
3. If they differ, prints to stderr:
   ```
   forge: this repo's methodology is v0.5.2; your CLI bundles v0.5.4. Run `forge upgrade` to refresh.
   ```
4. Suppressed by `FORGE_QUIET=1` env var or `--quiet` flag.

## 10. Legacy migration

`forge upgrade --migrate-claudemd` (one-shot; refused if `.forge/CONTEXT.md` already exists):

Migration only operates on root `CLAUDE.md` (the only agent root file v0.4 ever wrote). If the user wants Codex or Gemini support after migration, they invoke `forge upgrade --add-agent <kind>` separately.

1. Read root `CLAUDE.md`. Detect legacy single-file layout (any of these section headings present):
   - `## Forge principles`
   - `## Source of truth`
   - `## Skill ↔ verb contract`
   - `## Ephemeral ADR workflow`
   - `## Critical paths`
   - `## Branch strategy`
2. **Strict heading match**. For each expected heading, do a line-by-line SHA-256 comparison of the section's prose against the bundled v0.4 template. If any heading is missing, reordered, or its prose has drifted by even one byte → bail cleanly. Print the manual recipe and exit 0. Do not modify any file.
3. Save the original `CLAUDE.md` to `CLAUDE.md.pre-migration.bak` (before any writes).
4. Rewrite root `CLAUDE.md`: remove the legacy methodology sections, prepend the Forge prefix block (markers + breadcrumb + `@.forge/CONTEXT.md` import). Product-specific content (`## Stack`, `## Conventions`, etc.) is preserved verbatim.
5. Materialize `.forge/CONTEXT.md` from `templates/CONTEXT.template.md` + rendered CLI surface. Since step 2 guaranteed exact-match, the migrated content equals the bundled template — no user customizations are silently dropped (any customization would have failed the strict check and bailed at step 2).
6. Write `.forge/.version` and `.gitignore` marker block.
7. Print next-steps: "Commit `CLAUDE.md` and `.gitignore`. Other devs run `forge upgrade` after pulling to materialize their own `.forge/CONTEXT.md`."

Two-step migration is intentional:
- **Step 1 (one dev, one commit)**: trimmed `CLAUDE.md` + breadcrumb + marker block in `.gitignore`. Commits land on the branch.
- **Step 2 (each dev, locally)**: after pulling, run `forge upgrade` to materialize `.forge/CONTEXT.md`.

## 12. Acceptance criteria

Run each as a failing test against live code before closing scope.

### AC1 — `forge init` produces correct layout

Given a fresh empty git repo, `forge init` with all three agents selected produces:
- Tracked: `CLAUDE.md`, `AGENTS.md`, `GEMINI.md`, `.forge/settings.yaml`, `.gitignore` containing the marker block.
- Gitignored: `.forge/CONTEXT.md`, `.forge/.version`.
- `.forge/CONTEXT.md` content matches `bundled-template + rendered-registry` byte-for-byte.
- Each root file starts with the correct prefix marker block.

### AC2 — `forge upgrade` is a no-op on a clean repo

Run `forge init`, then immediately `forge upgrade`. Exit 0. All Forge-managed file contents are byte-for-byte identical to post-init state.

### AC3 — `forge upgrade` refuses on edited `.forge/CONTEXT.md`

Run `forge init`. Append "edited" to `.forge/CONTEXT.md`. Run `forge upgrade`. Exit 1, stderr contains diff, no files written.

### AC4 — `forge upgrade --force` overwrites with `.bak`

Same setup as AC3, but with `--force`. Exit 0, `.forge/CONTEXT.md` matches bundled template, `.forge/CONTEXT.md.bak` exists with the edited content.

### AC5 — Marker block rewrite preserves user prose

Run `forge init`. Edit `CLAUDE.md`, adding a "## My Product Rules" section at the bottom. Bump bundled methodology version. Run `forge upgrade`. Prefix block updated; "## My Product Rules" section unchanged.

### AC6 — `--migrate-claudemd` extracts cleanly

Given a v0.4-format combined `CLAUDE.md` (the current `templates/CLAUDE.project.template.md` rendered), run `forge upgrade --migrate-claudemd`. Result: trimmed `CLAUDE.md` + marker block + `CLAUDE.md.pre-migration.bak` + materialized `.forge/CONTEXT.md`. Original content recoverable from `.bak`.

### AC7 — `--migrate-claudemd` bails cleanly on drift

Given a `CLAUDE.md` where the user has edited "## Source of truth" prose, run `forge upgrade --migrate-claudemd`. Exit 0, no files written, manual recipe printed.

### AC8 — Drift warning fires on version mismatch

Run `forge init`. Manually edit `.forge/.version` to an older version. Run `forge orchestrate claim`. Stderr contains drift warning. `FORGE_QUIET=1 forge orchestrate claim` suppresses it.

### AC9 — Multi-agent: add later

Run `forge init` selecting only Claude Code. Run `forge upgrade --add-agent codex`. `AGENTS.md` appears at root with marker prefix; `.forge/settings.yaml` `agents.enabled[]` now includes `codex`.

### AC10 — Multi-agent: dogfood

This repo (`/Users/firatcandogan/repos/forge`) post-implementation has: trimmed `CLAUDE.md`, gitignored `.forge/CONTEXT.md`, the marker block in `.gitignore`. Methodology section of trimmed `CLAUDE.md` is empty (moved out).

## 13. Suggested implementation phasing

The refactor is coherent but large enough that the implementation plan should split it. Suggested phases (the planner decides final shape):

**Phase A — Split + dogfood (no upgrade verb yet)**
- New `templates/CONTEXT.template.md`.
- Trim `templates/CLAUDE.project.template.md`. Add sibling templates for AGENTS / GEMINI.
- Add `src/cli/registry.ts` + render-context module.
- Refactor `src/cli/init/scaffold.ts` for multi-agent selection.
- Add `agents.enabled[]` to settings schema.
- New `gitignore-block.ts` shared writer.
- Dogfood: apply the split to this repo's own `CLAUDE.md`.
- All AC1, AC10 pass.

**Phase B — Upgrade + drift + agent management**
- New `forge upgrade` verb (no-op, refusal, --force).
- `.forge/.version` write + drift-warning pre-hook.
- `--add-agent` / `--remove-agent` flags.
- AC2, AC3, AC4, AC5, AC8, AC9 pass.

**Phase C — Migration**
- `forge upgrade --migrate-claudemd` (strict-match-only).
- Manual-recipe fallback path.
- AC6, AC7 pass.

Phase A is mergeable independently (the repo can ship with the split layout but no re-sync verb; users edit `.forge/CONTEXT.md` manually until B lands).

## 14. Out of scope

- **Postinstall hook on `@firatcand/forge`** that touches cwd. npm best-practice forbids this; we keep init explicit.
- **Auto-fetching forge from the user's GitHub link in the breadcrumb.** The breadcrumb is informational only; the user runs `npm install` themselves.
- **A `forge downgrade` verb.** Methodology versions only move forward.
- **Pinning methodology to a specific version per repo (e.g., `.forge/methodology-version-pin`).** Could be added later; not needed for v0.5.
- **Editing arbitrary user prose under methodology headings.** Migration is strict-match-only; anything that doesn't match exactly bails cleanly to manual recipe.

## 15. Risks & mitigations

| Risk | Likelihood | Mitigation |
|------|------------|------------|
| Claude Code's `@import` syntax changes or is removed | Low | Prefix block is markdown content, not a runtime feature; if `@import` breaks, the breadcrumb still conveys the directive. We can switch to prose-directive form (same as AGENTS.md) in a future version via `forge upgrade`. |
| Codex / Gemini agents ignore the prose directive to read `.forge/CONTEXT.md` | Medium | We test against each agent's actual context-loading behavior during v0.5 QA. Fallback: emit the methodology inline into AGENTS.md/GEMINI.md (loses the gitignored property for those agents, but keeps the team coherent). |
| User's `.gitignore` is highly customized; marker block placement causes merge conflicts | Low | Marker block is delimited; we never touch lines outside the markers. If markers exist, we replace in place; if not, we append. Idempotent. |
| Migration heuristic (heading-text match) misfires on a customized v0.4 CLAUDE.md | Medium | Strict-match-only. Bails cleanly when uncertain, prints manual recipe. Never destructive without `--force`. |
| Existing Forge repos break on first `forge upgrade` because their `CLAUDE.md` is mid-customization | Low | `--migrate-claudemd` is explicit and one-shot; default `forge upgrade` refuses if it detects legacy single-file layout (no `.forge/CONTEXT.md` and methodology sections still in CLAUDE.md). |
| Multi-agent root file content drifts (user edits `CLAUDE.md` product content but not `AGENTS.md`) | Medium | This is acceptable — each agent's root file is product-owned. We do not auto-sync product content across them. Users can configure CI to flag drift if desired. |

## 16. Deferred decisions

- Whether `forge upgrade` should automatically run `git add` on the changed files (helpful, but breaks "never auto-commit" expectation). Default: no.
- Whether the breadcrumb should also link to forge ETHOS.md. Probably yes; trivial template change.
- Whether `.forge/CONTEXT.md` should be split into multiple files (e.g., `principles.md`, `cli-surface.md`) to improve diff readability on upgrade. Defer until the rendered file exceeds ~1k lines.
